# 고정 질문 리서치 리포트 — 회차·배치 실행

`signal-report-setup`으로 만든 프로젝트에서 쓴다. 참조 구현은 두 개다: skykelly/axblog(초기 구조, 판정 게이지), skykelly/kr_electronics_market(최신 구조: 분석 전망, 통합 질문의 교차 인용, 일간 Diff, 배치 입력 도구). 시작 전에 저장소 루트의 `README.md`, `CLAUDE.md`, `site/catalog.json`, 대상 질문의 카테고리 `README.md`와 최신 `request_rN.md`를 읽는다. 프로젝트 문서의 규칙이 이 스킬과 다르면 프로젝트 문서를 따른다. 작업 전 `git pull`.

## 모드

요청이나 예약 작업이 어느 모드인지 정한다.

| 모드 | 언제 | 만드는 기록 | 아티클 | 변경 이력 |
|---|---|---|---|---|
| 딥리서치 회차 | 요청 시(한 번에 1~3개 질문, 월 2~3개 권장) 또는 프로젝트 순환표 | 4유형 모두 | 새 회차 `article_rN.html` | 회차 1줄 |
| 일간 배치 | 매일 정한 시각 | 신규 사건·지표, 기간·조건 갱신, 마감 전망 판정 | 현재 회차 갱신 | 그날 항목 |
| 주간 배치(또는 주간 간단 조사) | 매주 정한 요일 | 30일 안 마감 전망 판정, '확인 필요' 3~5건 해소, 주간 요약. 일간 배치가 없는 프로젝트면 아래 B의 일도 함께 | 현재 회차 갱신 | 그날 항목 + 요약 메모 |
| 검증 탐침 | 기준 회차 직후, 이후 분기마다 또는 요청 시 | 기록을 바꾸지 않고 보고서만 | 없음 | 없음 |

## 공통 판단 규칙 (모든 모드)

- **근거 없는 추측 금지, 근거 있는 정리는 적극:** 회사 의도·원인 추정, 가설은 쓰지 않는다. 해석은 사실 기록 2건 이상을 `basis`로 묶어 패턴·비교·전환점·구간별 특징·주체 간 차이를 쓴다. 증감만 나열하는 글은 실패로 본다.
- **인과 대신 시간 순서:** 조치와 지표 변화를 연결할 때는 "같은 시기", "이후"처럼 순서만 쓰고 "보완했다", "노렸다" 같은 의도 표현을 피한다. 필요하면 "시간 순서만 확인되며 인과는 확인하지 않았다"를 적는다.
- **출처 유형:** 지표·사건마다 `claim_type`(자사 집계 / 외부 검증 / 공시 / 해당 없음). 자사 집계는 `external_check`에 외부 검증 출처 또는 '미확보'. 회사 자체 집계를 시장 사실처럼 쓰지 않는다.
- **지역·범위 혼용 금지:** 글로벌·전사 수치를 대상 지역 성과로 쓰지 않는다. 꼭 남겨야 하면 `region`에 범위(예: 전사, 한국 단독 아님)를 적고 문장에도 쓴다. 대상 지역 값이 없으면 `meta.json`의 `unknowns`로.
- **단정 금지:** 원문을 직접 열지 못한 값, 정의가 다른 값, 출처끼리 다른 값은 차이를 병기하고 `check_flags`에 사유를 남긴다. 범위 값(예: 40%대 후반)을 숫자 칸에 넣을 때는 표기용 값임을 flag로 밝힌다.
- **요약 도구 결과 주의:** 웹 페이지 요약은 작은 모델이 만든다. 핵심 수치는 두 출처로 맞춰 보고, 열리지 않은 페이지는 실패로 적고 `unknowns`에 남긴다.
- **문체:** 짧은 보고체, 줄표로 문장 잇지 않기, 비유·과장 없음, 약어는 처음에 풀어 쓰기. 본문에는 사실과 기준만 쓰고 과정 문구("검증 결과에 따르면")는 넣지 않는다.

## 전망은 두 종류

- **회사 계획:** 회사·기관이 공식 발표한 목표·계획. `announced_by`(발표 출처 URL) 필수. 이행/미이행/변경/만료로 추적.
- **분석 전망:** 리포트가 세우는 판정 가능한 전망. 작성일(`made_on`, 실제 작성일)로부터 6~18개월 안의 `due`, `condition`(맞음·틀림·판정 불가 조건), `method`(판정 방법), `reasoning`(예측 근거), `counter`(틀릴 수 있는 이유), 가능하면 `history`(과거 반복 횟수). `basis`는 사실 기록 2건 이상 + 해석 1건 이상. 판정은 맞음/틀림/판정 불가. 틀린 전망도 지우지 않는다. 회사 의도 추정은 예측 근거로 쓰지 않는다.
- 질문당 분석 전망 3~5개. 반복될 사건, 기준을 넘을 수치, 유지될 공시·발표 형식처럼 기록으로 판정할 수 있는 문장만.

## A. 딥리서치 회차 (R번호 +1)

질문 하나씩 충분히 한다. 질문당 직접 연 원문 30건 이상, 기록 30건 이상을 목표로 하고 질문이 다루는 기간에 빈 구간을 남기지 않는다.

1. **요청서 `request_rN.md`:** 고정 질문, 한 줄 답 형식, 조사 기간(직전 회차 이후 + 지표는 최신 공개값), 추적 지표 표, 출처 기준, 미확인 단서(`python3 tools/intake.py leads 질문`). 이전 아티클과 이전 판정은 넣지 않는다.
2. **조사:** 공식 발표·공시·주요 언론에서 연도별로 빈 곳 없이 모은다. 하위 에이전트를 쓰면 질문 하나에 하나, 요청서 전문을 넘기고 출처 링크가 달린 보고서를 받는다(사용자가 하위 에이전트를 원하지 않으면 직접 조사). 보고서는 회차 자료로 보관(공개 저장소면 요약만).
3. **4유형 추출과 원문 확인:** 지표·사건은 원문을 다시 열어 수치·날짜가 실제로 있는지 확인하고 `verified`를 채운다. 확인 못 하면 '확인 필요'. 해석은 basis, 전망은 위 필수 필드가 없으면 버린다.
4. **기록 작성:** 질문별 build 스크립트(예: `tools/<q>/<q>_build.py`)에 사건 `ev`, 지표 `me`, 해석 `it`, 분석 전망 `af`, 회사 계획 `cp`를 쓰고 출처는 공용 출처 표(예: `tools/c1/c_src.py`)에 키로 추가한다. 빌더가 ID(`질문-E/M/I/F-NNN`)를 매기고 `records_base.jsonl`과 키→ID 표(`<q>_amap.json`)를 만든다. 작성일은 `b.ON`에 실제 날짜로.
5. **DB 대조와 점검 (초안을 쓰지 않은 눈으로):**
   - 새 기록과 기존 기록 짝짓기: 지표는 T번호·지역·정의, 사건은 주체·일자·내용, 해석은 대상·방향. 뜻이 같으면 새로 만들지 않는다
   - 빠진 중요 사실: 중요도 2 이상 유효 기록이 이번 조사에 없으면 보완 조사 대상
   - 모순된 해석: 이전과 반대 방향인데 새 근거가 없으면 이전 해석 유지 + 플래그
   - 수치 충돌: 같은 지표 다른 값은 둘 다 기록하고 등급 높은 쪽을 대표값으로
   - 만기 전망: method대로 판정
   - **다른 질문과 대조:** 같은 주제(브랜드·카테고리·수치)를 다른 질문 기록에서 검색해 빠진 사실, 상충 값을 찾는다
6. **보완 조사:** 위에서 나온 빈 곳만 짧은 검색으로 확인한다.
7. **meta.json:** `one_line`(+basis), `rows`(한 줄 답 형식의 칸), `insights`(제목·문장·basis), `narrative`(시기별 소제목, 문단마다 basis), `ledger`(원장 표: 열·행·basis, 단계·분류 기준은 note), `indicators`, `events_lead`, `unknowns`(항목·왜 필요한가). 메타 스크립트(`<q>_meta.py`)는 amap으로 키를 ID로 바꾼다.
8. **검증:** `python3 lib/build_records.py <질문 폴더>`. 해석 basis 2건 이상(사건·지표), 분석 전망 basis(사실 2 + 해석 1)와 마감 6~18개월, 회사 계획 announced_by, 자사 집계 external_check, 변경 종류(`lib/records.py`의 KIND_ORDER: 판정, 누락정정, 단정반증, 전망 교체, 판정 기준 보완, 상충, 전망 점검, 갱신, 신규, 삭제)를 확인한다.
9. **렌더:** `python3 lib/render_article.py <질문 폴더>`. 아티클 순서: 한 줄 답 → 인사이트 요약 → 서술형 해석 → 원장 표 → 연표 → 지표 → 해석 기록 → 분석 전망 → 예측 근거 → 회사 공식 계획 → 다른 질문에서 인용한 기록 → 미확인 → 경고. 판정 게이지를 쓰는 프로젝트(axblog형)는 판정 기준표로 다시 판정하고 `signal_rN.json`을 낸다.
10. **포털·마무리:** 카테고리 README 진행 상황 갱신 → `python3 site/build_site.py`(깨진 링크 0) → PC(1280)·폰(400) 폭에서 가로 넘침(scrollWidth)과 화면 확인 → 커밋 → 포털 재게시.
11. **변경 이력:** 일간 Diff 구조가 있으면 `python3 lib/diff_day.py --round <질문>`으로 회차 1줄만 남긴다(기록 수백 건이 '신규'로 쏟아지지 않게).

## 통합 질문 (다른 질문 기록을 묶는 질문)

주체별 행동 질문(전략·제품·채널·판촉·AS 등) 위에 결과·조건 질문(시장 수치, 경쟁 구도 전환, 고객 선택 조건, 규제·정책)을 둘 때 쓴다.
- 사실을 복사하지 않고 다른 질문의 기록 ID(예: `C3-E-053`)를 basis로 인용한다. 검증은 다른 질문의 records.jsonl도 읽고, 아티클은 인용 기록을 원래 질문 페이지로 링크하며 '다른 질문에서 인용한 기록' 칸을 만든다.
- 새로 조사하는 것은 결과를 보여 주는 증거(가격, 점유율, 설문, 통계, 제도 문서)뿐이다. 신규 원문이 30건에 못 미치면 인용 기록으로 보완하고 보고에 그 사실을 적는다.
- 원장 표에는 단계·분류 기준을 note로 명시한다(예: 진입 = 출시 확인, 확장 = 양판점 입점 또는 판매 순위 상위, 우위 = 점유율 1위 보도).

## B. 일간 배치

1. `git pull`. 각 질문 records.jsonl의 최근 기록으로 중복을 확인한다.
2. 수집처(프로젝트 CLAUDE.md 목록)를 직전 changelog 날짜 다음 날부터 오늘까지 훑고, 찾은 사건을 질문에 배정한다. 원문을 직접 연 것만 반영한다.
3. 반영은 `tools/daily.py`로 한다: `add <질문 폴더> '<기록 JSON>'`(ID 자동), `revise <폴더> <ID> <종류> '<이유>' '<set JSON>'`, `judge <폴더> <전망 ID> <판정> '<결과>'`. 도구가 바로 검증하고 실패하면 되돌린다. `records_base.jsonl`과 build 스크립트는 고치지 않는다.
4. 판단이 애매한 것은 반영하지 않고 보고에 '단서'로 적는다(무인 실행이므로).
5. 바뀐 질문만 render → `site/build_site.py` → `python3 lib/diff_day.py`(변화가 없어도 실행해 '변화 없음'을 남김) → 다시 `site/build_site.py` → 커밋·push → 재게시.
6. 보고: 신규 N · 갱신 N · 판정 N, 신규 사건 목록(질문 번호와 한 줄), 확인 필요·단서 목록. 변화가 없으면 "변화 없음"과 확인한 수집처 범위.

## C. 주간 배치 (주간 간단 조사)

1. 진행 중이고 30일 안에 마감되거나 이미 마감된 전망을 원문으로 판정한다(`tools/daily.py judge`).
2. check_flags가 있는 기록 중 중요도 높은 3~5건의 원문(A·B)을 찾아 `revise`로 해소한다(누락정정·단정반증·상충).
3. 값이 빈 추적 지표, 이번 주 발표된 공식 통계(지표 표의 발표 시기 참조), 수동 입력 단서(leads)를 확인한다.
4. 지난 7일 changelog를 요약해 `python3 lib/diff_day.py --note "주간 요약: ..."`.
5. render → build_site → 커밋 → 재게시. 보고: 판정 내역, 해소 건수, 다음 30일 마감 전망, 회차 재조사 후보.

해석·분석 전망의 근거가 바뀌면 그 자리에서 결론을 바꾸지 말고 '전망 점검' revision과 '확인 필요'를 남겨 다음 딥리서치에서 다룬다. 판정이 매주 흔들리지 않게 하기 위해서다.

## D. 검증 탐침

1. 질문마다 기록을 보지 않고 같은 요청서로 백지 재조사 → `probe_YYYYMMDD/blind_질문.md`
2. 백지 결과와 기록을 대조해 `findings_질문.jsonl`: `{cls(변경 종류), ref(기록 ID), importance, impact(판정 영향|문장 수정|참고), statement, note, sources}`
3. `verification_report.md`: 판정 영향 → 문장 수정 → 참고 순서, 항목마다 출처 등급과 확인 범위
4. 기록은 바꾸지 않는다. 보고서를 사용자에게 보여 주고 승인한 항목만 다음 반영 때 적용한다(프로젝트 CLAUDE.md가 다르게 정했으면 그대로).

## 변경 이력 원칙

- 변경 이력은 기록에서 다시 만들지 않는다. 기준선 스냅숏(`state/snapshot.json`)과 날짜별 파일(`changelog/<YYYY-MM-DD>.json`, 추가만)이 원본이다.
- 담는 것: 신규, 갱신, 판정, 정정(누락정정·단정반증·상충 등), 삭제. 이전 문장과 이유를 함께. 회차 재조사는 1줄, 변화 없는 날은 '변화 없음' 1줄.
- 게시된 기록의 ID는 바꾸지 않는다. 질문을 다시 빌드할 때도 기존 키 순서가 바뀌지 않게 하고, 늦게 찾은 기록은 add 패치로 뒤 번호를 쓴다.

## 하위 에이전트 지시서에 반드시 넣을 것 (쓰는 경우)

- 요청서 전문, 기록 형식(필드·ID 규칙), 출처 등급 정의, 공통 판단 규칙
- 원문을 직접 연 것만 verified, 수치·날짜를 지어내지 않기
- 결과 반환 형식(보고서 마크다운 또는 jsonl)과 파일 경로
- 다른 파일은 고치지 않기, 커밋·게시 금지(본 세션이 한다)

## 포털 게시

- 게시 전 Artifact read로 바뀐 경로(또는 manifest의 pages)를 읽는다. 읽지 않은 파일이 있으면 게시가 거부된다.
- 진입 페이지 `site/dist/artifact_index.html`, root `site/dist`, files는 `site/dist/manifest.json`의 pages 전부. capabilities는 생략해 유지한다(`{}`를 넘기면 AI Chat이 꺼진다).
- 공통 스크립트(AI Chat 등)를 고쳤으면 모든 페이지를 함께 올린다.
