# 고정 질문 리서치 리포트 — 수동 자료 입력

사용자가 대화로 준 자료(기사, 보고서 파일, 링크, 다른 AI의 딥리서치 결과, 메모, 문장 지적)를 프로젝트 기록에 넣는다. 도구는 프로젝트의 `tools/intake.py`(참조 구현: skykelly/axblog, skykelly/kr_electronics_market). 시작 전 `CLAUDE.md`의 수동 입력 절차와 공통 판단 규칙, `site/catalog.json`을 읽고 `git pull`.

기본 모드는 **검토 후 반영**이다. 사용자가 "바로 반영"이라고 할 때만 검토 카드를 건너뛴다.

## 절차

1. **보관:** `python3 tools/intake.py stage 파일 --title .. --slug 영문 [--author --date --url --grade]`
   - 원본은 `inbox/`(git 제외)에만 둔다. 공개 저장소에는 남의 글 전문이나 사내·비공개 자료를 커밋하지 않는다.
   - 붙여 넣은 텍스트는 먼저 파일로 저장한 뒤 stage한다.
2. **주장 추출과 질문 매핑:** 자료의 주장을 한 문장씩 뽑아 catalog의 질문에 붙인다. 사실 기록은 그 사실의 주제 질문(주체별 행동 질문 등)에 넣고, 결과·조건을 묶는 통합 질문은 그 기록을 인용하게 한다. 어느 질문에도 안 맞으면 "범위 밖"으로 표시한다.
3. **기존 기록 대조:** 주장마다 일치(재확인) / 갱신 / 상충 / 신규로 나눈다. 다른 질문에 같은 사실이 있는지도 검색해 중복 기록을 만들지 않는다.
4. **원문 확인:**
   - 자료가 C등급이거나 URL이 없으면 주장마다 원문(A·B)을 찾는다. 확인된 범위만 기록 문장으로 쓴다.
   - 사용자 메모·관찰은 사실 기록이 아니라 단서(lead)로 받는다. 원문을 찾으면 기록으로 올린다.
   - 다른 AI의 딥리서치 결과도 같은 기준이다. 인용된 원문을 다시 열어 확인한다.
   - "이 문장 틀렸어" 같은 지적은 근거를 확인한 뒤 누락정정·단정반증으로 반영한다.
   - 회사 자체 집계는 `claim_type: 자사 집계`와 `external_check`를 단다. 글로벌·전사 수치는 대상 지역 성과로 쓰지 않는다.
5. **후보 작성:** `intake/ID.proposal.json` 항목:
   - 수정: `{n, q, op:"revise", id, kind, why, set, add_sources, add_flags, add_basis, impact, claim, status}`
   - 추가: `{n, q, op:"add", record:{전체 기록, ID는 그 질문의 다음 번호(tools/daily.py next-id)}, impact, claim, status}`
   - 단서: `{n, q, op:"lead", claim, reason}`
   - `kind`는 KIND_ORDER(판정, 누락정정, 단정반증, 전망 교체, 판정 기준 보완, 상충, 전망 점검, 갱신, 신규, 삭제)만. `impact`는 판정 영향 | 문장 수정 | 참고. 원문 전문은 넣지 않는다.
6. **검토 카드:** `python3 tools/intake.py preview ID` 결과를 채팅에 그대로 보여 주고 승인을 받는다. 판정 영향 항목을 맨 위에 둔다.
7. **반영:** `python3 tools/intake.py apply ID [--only 1,2 | --skip 3]` → 질문별 `daily.jsonl`에 쓰이고 `build_records.py`가 patches 다음에 적용한다(회차 build 스크립트가 덮어쓰지 않는 파일). 프로젝트가 아직 patches.jsonl 방식이면 그 방식을 따른다. 게시된 기록의 ID는 바꾸지 않는다. 출력의 "meta.json에서 확인할 곳"을 보고 한 줄 답·인사이트·원장 문장을 맞춘다.
8. **마무리:** render → `python3 site/build_site.py`(깨진 링크 0) → `python3 lib/diff_day.py`(그날 변경 이력에 '제공 자료'로 쌓임) → 다시 build_site → PC·폰 폭 확인 → 커밋 → 포털 재게시(게시 전 Artifact read, capabilities 생략).
9. **추적:** `intake.py list`(접수 목록), `intake.py leads [질문]`(미확인 단서, 다음 회차 요청서와 일간 배치 보고에 넣는다).

## 판정에 영향이 갈 때

수동 입력으로 해석이나 분석 전망의 결론이 바뀔 만하면 바로 바꾸지 않는다. 근거 기록만 넣고 '확인 필요' 플래그와 '전망 점검' revision을 단 뒤 다음 딥리서치 회차로 넘긴다. 마감된 전망의 결과가 자료로 확인되면 판정(분석 전망은 맞음·틀림·판정 불가, 회사 계획은 이행·미이행·변경·만료)을 반영할 수 있고, 틀린 전망도 지우지 않는다. 사용자가 즉시 반영을 원하면 근거를 보여 주고 승인을 받는다.

## 보고

접수 ID, 추출 주장 수, 반영·건너뜀·단서 건수, 질문별 변경, 판정 영향 여부, 남은 '확인 필요' 목록, 포털 갱신 여부. 짧은 보고체, 줄표로 문장 잇지 않기.
