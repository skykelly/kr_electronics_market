# 고정 질문 리서치 리포트 — 새 프로젝트 만들기

주제 하나를 "고정 질문 → 주기적 재조사 → 4유형 기록(지표·사건·해석·전망) → 아티클과 일간 Diff → 포털"로 운영하는 프로젝트를 처음부터 세운다. 회차·배치 실행은 `signal-report-round`, 자료 수동 입력은 `signal-report-intake` 스킬이 맡는다.

참조 구현: skykelly/axblog(AX Signals, 초기 구조와 판정 게이지), skykelly/kr_electronics_market(KR Appliance Signals, 최신 구조). 새 프로젝트는 최신 구조를 기준으로 하고, 판정 게이지가 필요한 주제면 axblog의 `lib/judge.py`를 가져온다. 코드를 새로 짜지 말고 저장소를 읽기 전용으로 받아 필요한 파일을 복사·수정한다.

## 핵심 원칙 (모든 단계에 적용)

- **원본은 기록 파일:** 질문별 `records_base.jsonl`(회차 조사) + `patches.jsonl`(회차 보정) + `daily.jsonl`(배치·수동 입력)을 `lib/build_records.py`가 검증해 `records.jsonl`을 만든다. 아티클·포털은 결과물이다. 변경 이력만은 예외로 `changelog/<날짜>.json`이 원본이다(기준선 이후 매일 쌓임).
- **근거와 판단의 분리:** 지표·사건은 원문 링크를 갖고, 해석·전망은 사실 기록 번호(`basis`)에 연결한다.
- **근거 없는 추측 금지, 근거 있는 정리는 적극:** 해석은 기록 2건 이상으로 패턴·비교·전환점·차이를 쓴다. 증감만 나열하지 않는다.
- **전망 두 종류:** 회사 계획(공식 발표, announced_by)과 분석 전망(6~18개월 마감, 조건·판정 방법·예측 근거·반론·과거 반복, basis 사실 2 + 해석 1). 틀린 전망도 지우지 않는다.
- **출처 유형:** `claim_type` 자사 집계 / 외부 검증 / 공시. 자사 집계는 `external_check` 필수.
- **범위 혼용 금지:** 글로벌·전사 수치를 대상 지역 성과로 쓰지 않는다. 값이 없으면 `unknowns`.
- **본 조사는 백지에서:** 딥리서치는 이전 글을 보지 않는다. 이전 기록과의 대조는 그다음 단계에서 한다.
- **비교 가능성:** 질문과 추적 지표를 고정한다. 질문·지표는 분기에 한 번만 바꾸고, 바꾸면 버전을 올린다.
- **출처 등급:** A = 1차 조사·공식 발표·정부 통계·공시, B = 주요 언론·2차 보도·컨설팅, C = 블로그·출처 불명(단독 근거 금지).
- **단정 금지:** 원문을 직접 열지 못한 값, 정의가 다른 값, 확신이 낮은 값은 단정하지 않고 `check_flags`에 사유를 남긴다.

## 0. 먼저 정할 것 (AskUserQuestion으로 한 번에)

1. 주제와 독자: 누가 무엇을 판단하려고 읽는가
2. 카테고리 수(1~4)와 이름, 질문 번호 접두어(예: S1~, C1~, X1~)
3. 저장 위치: 새 GitHub 저장소(이름) 또는 연결된 로컬 폴더. 공개 저장소면 남의 글 전문·사내 자료를 커밋하지 않는다는 점을 알린다
4. 포털 필요 여부와 대표 색. 같은 사용자의 다른 시그널 포털과 첫 화면이 구분되게 한다(머리 영역 색 띠, 레이더 유무 등)
5. 주기: 기본은 일간 배치 + 주간 배치 + 요청 시 딥리서치. 실행 시각
6. 지역 렌즈: 한국 중심인지, 글로벌 선행 + 한국 확인인지

대답이 없으면 기본값으로 진행하고, 무엇을 가정했는지 첫 보고에 적는다.

## 1. 질문 설계 (사용자 승인 필수)

두 층으로 설계한다.
- **행동 질문:** 주체별(회사·브랜드·기관) 전략, 제품, 채널, 판촉, 서비스처럼 "무엇을 했는가"를 시간순으로 쌓는 질문. 카테고리마다 3~7개.
- **결과·조건 질문:** 시장 수치(무엇이 일어났나), 경쟁 구도 전환(왜 움직였나), 고객 선택 조건(고객 쪽 조건), 규제·정책(바깥 조건)처럼 행동 질문의 기록을 묶어 결론을 내는 질문. 가격표·불만 건수 같은 미시적 수치 목록이 되지 않도록, 그 수치가 무엇을 판정하는 증거인지로 질문을 쓴다. 다른 질문 기록을 basis로 인용한다.

각 질문에 정한다.

| 항목 | 규칙 |
|---|---|
| 질문 | 상태를 묻는 한 문장. "어디까지 왔는가", "무엇이 늘고 줄었는가", "누가 주도하는가" |
| 한 줄 답 형식 | 매 회차 같은 틀(예: 단계 판정, 순위, 방향×속도, 시장 조건표 + 카테고리×주체 수치표) |
| 원장 표 | 아티클 가운데 둘 표의 열 정의(예: 시기·주체·이벤트·구분·기간·채널·혜택). 단계 분류를 쓰면 기준을 note로 |
| 판정 척도(쓰는 경우) | 질문 성격에 맞게 고른다(아래). 판정 기준표: 단계마다 뜻, 수치 기준, 인정하는 근거. 간접 근거로 판정한 칸은 '잠정' |
| 추적 지표 3~10개 | ID `질문-T1~`, 이름, 단위, 정의, 우선 출처, 발표 주기 |

판정 척도 고르기:
- 기술·서비스 확산형: 채택 4단계(실험·얼리어답터·확산·주류), 수치 기준 10/25/50%
- 인구·가구·생활 통계형: 방향(증가·정체·감소) × 속도(가속·유지·둔화), 기준은 최근 3~5년 추세 대비
- 수요·원인형: 영향 순위(1~N위)와 순위 변동
- 경쟁·주도권형: 접점별 주도 주체 지도, 카테고리별 전환 단계(진입·확장·우위)

통계 주제는 공식 통계의 발표 시기를 지표 표에 적어 두고 해당 월에 먼저 찾게 한다. 발표 시기는 기억으로 쓰지 말고 조사해서 적는다.

예시 (한국인의 거주 형태·가족·생활 변화, 초안): 거주 형태가 어떻게 바뀌는가(자가·전월세·1인 주거·공유 주거), 가족 구성이 어떻게 바뀌는가(1인·부부·한부모·비혼 동거·다문화), 생활 사건의 시기와 빈도가 어떻게 바뀌는가(독립·혼인·출산·은퇴·돌봄), 하루의 시간과 생활 방식이 어떻게 바뀌는가(맞벌이·재택·가사 외주화), 그 변화가 어떤 새 수요를 만드는가. 실제 질문은 사용자와 확정한다.

질문·지표·원장 형식·기준표를 표로 보여 주고 승인을 받은 뒤에만 다음 단계로 간다. 이후 바꾸기 비싼 결정이기 때문이다.

## 2. 저장소 뼈대

1. 참조 구현을 읽기 전용으로 받는다(작업 폴더 밖 스크래치 위치에 `GIT_LFS_SKIP_SMUDGE=1 git clone --depth 1 ...`).
2. 복사해 고칠 것:
   - `lib/records.py`(KIND_ORDER: 판정, 누락정정, 단정반증, 전망 교체, 판정 기준 보완, 상충, 전망 점검, 갱신, 신규, 삭제 / patches 적용 / `load_external` 교차 인용), `lib/build_records.py`(검증, patches → daily 순서 적용), `lib/render_article.py`, `lib/article.css`, `lib/diff_day.py`(일간 Diff). 판정 게이지가 필요하면 `lib/judge.py`
   - `tools/c1/c_lib.py`(빌더: ev·me·it·af·cp·finish, 작성일 `b.ON`), 공용 출처 표 `c_src.py`, `tools/daily.py`(배치 입력: add·revise·judge·next-id, 검증 실패 시 되돌림), `tools/intake.py`(수동 입력, daily.jsonl에 씀)
   - `site/`(`build_site.py`, `changes.py`(changelog 파일만 읽음), `menu.py`, `portal.py/js/css`, `article_ui.html`, `chat.html`, `catalog.json`). 제목·소개 문구·색·카테고리를 새 주제로
   - `.claude/settings.json`: WebFetch·WebSearch·Agent 허용
3. 질문 폴더 `카테고리/질문id/`: `request_r1.md`, `records_base.jsonl`, `patches.jsonl`, `meta.json`, 배치가 만드는 `daily.jsonl`, 생성물(`records.jsonl`, `article_rN.html`, `signal_rN.json`). 질문별 빌드·메타 스크립트는 `tools/<질문>/`.
4. `README.md`: 주제 표, 질문 번호 규칙, 운영 원칙, 주기 표, 변경 이력 원칙, 회차 흐름, 포털 주소
5. `CLAUDE.md`: 공통 판단 규칙, 일간·주간 배치 절차, 회차 재조사, 포털 게시, 수동 입력 절차. 참조 구현의 CLAUDE.md를 주제에 맞게 고친다
6. 카테고리별 `README.md`: 질문 표(번호·질문·한 줄 답 형태·상태)와 질문별 진행 상황

## 3. 기록 형식 (records.jsonl 한 줄 = 한 기록)

공통: `question, question_version, id(질문-M/E/I/F-NNN), type(지표|사건|해석|전망), importance(1~3), statement, added_on(실제 날짜), first_seen, status(유효|미확인|대체됨|반박됨), check_flags[], sources[{url,publisher,date,grade}], verified, claim_type, external_check, revisions[{on,kind,before,why}]`

- 지표: `indicator(T번호), value, unit, as_of, region`
- 사건: `date, actor, event_type`(예: 전략·조직, 제품 출시, AI·연결, 마케팅, 채널·매장, 판촉, 구독·케어·AS, 제휴·협업, 실적·시장, 인증·규제, 기타), `recurrence`(정기|비정기), 필요하면 `period_start/end, channel, benefit, product, message`
- 해석: `target, direction(강화|약화|중립), basis[]`(사실 2건 이상, 다른 질문 ID 가능)
- 전망: `forecast_kind`(회사 계획|분석 전망), `due, method, forecast_status, result`, 회사 계획은 `announced_by`, 분석 전망은 `made_on, condition, reasoning, counter, history, basis[]`

`meta.json`: `one_line, one_line_basis, rows, insights, narrative, ledger{title,note,columns,rows}, indicators, events_lead, unknowns[{item,why}]`.

`build_records.py`가 규칙을 검증한다(근거 연결, ID 중복, 출처 등급, 변경 종류, 전망 필수 필드와 마감 범위). 실패하면 기록을 고친다.

## 4. 기준 회차 R1

`signal-report-round`의 딥리서치 회차를 질문마다 실행한다. 한 번에 1~3개 질문, 질문당 원문 30건·기록 30건 기준. 행동 질문을 먼저 끝내고 결과·조건 질문을 나중에 만들어 교차 인용을 쓴다. 각 질문을 끝낼 때 다른 질문 기록과 대조해 빠진 사실·상충 값을 확인한다. 끝나면 우선 카테고리에 검증 탐침을 한 번 돌린다.

## 5. 변경 이력 기준선

R1 전체가 끝나면 `python3 lib/diff_day.py --baseline`으로 기준 스냅숏과 첫 changelog(기준선 1줄)를 만든다. 그 이전 작업은 이력에 남기지 않는다. 이후 배치가 매일 그날 바뀐 것만 쌓는다.

## 6. 포털

1. `python3 site/build_site.py` — 깨진 내부 링크 0이어야 통과.
2. Artifact로 게시: 진입 페이지 `site/dist/artifact_index.html`, root `site/dist`, files는 manifest의 pages 전부. 첫 게시 주소를 README와 CLAUDE.md에 적는다. 이후 게시 전에는 항상 read로 최신본을 읽는다.
3. AI Chat(`chat.html`)은 포털·아티클·변경 이력 모든 페이지에 넣는다. 아티클 페이지에는 현재 질문 번호를 맥락으로 넘기고 추천 질문을 바꾼다. `sample` 기능을 첫 게시에 선언하고 이후 capabilities는 생략해 유지한다(`{}`를 넘기면 꺼진다).
4. 첫 화면 머리 영역은 프로젝트마다 다른 색 띠로 구분한다. 화면 끝까지 칠할 때는 `border-image: linear-gradient(...) fill 0 / 0 / 0 100vmax`를 쓴다(box-shadow·가상 요소 확장은 가로 스크롤을 만든다).
5. PC(1280)·폰(400) 폭, 밝은·다크 모드에서 `scrollWidth`가 폭을 넘지 않는지, 콘솔 오류가 없는지 확인한다.

## 7. 정기 실행 등록

예약 작업 두 개(사용자에게 시각 확인, 정각을 피해 몇 분 앞당김):
- 일간 배치: "저장소를 붙이고 CLAUDE.md의 일간 배치 절차를 따른다"처럼 단독으로 이해되게 쓴다. 수집처, tools/daily.py 사용, diff_day 실행, 재게시, 보고 형식을 프롬프트에 넣는다. 판단이 애매하면 단서로만 보고하게 한다.
- 주간 배치: 마감 전망 판정, 확인 필요 해소, 주간 요약, 회차 재조사 후보 보고.
월간 딥리서치는 품질을 위해 요청 시 진행한다(순환표로 자동화하려면 README에 순환표를 적고 "이번 순번의 질문을 딥리서치 회차로 실행"하게 한다). 각 작업의 승인 모드를 한 문장으로 알린다.

## 지난 프로젝트에서 배운 함정

- 마크다운 굵게: 닫는 `**` 앞이 문장부호이고 뒤가 한글이면 렌더되지 않는다. 문장부호를 굵게 밖으로 뺀다.
- `10~20%(1,900억~3,850억)`처럼 물결표가 두 번 나오면 취소선이 된다. 렌더러에서 단일 `~`를 이스케이프한다.
- 표 칸의 한글 단어가 한 글자씩 끊기면 `word-break:keep-all; overflow-wrap:break-word`.
- HTML에 넣는 JS 문자열 안의 큰따옴표를 이스케이프하지 않으면 스크립트 전체가 죽는다. 생성된 페이지의 `<script>`를 뽑아 `node --check`로 확인한다.
- `display:grid` 같은 작성자 CSS는 `hidden` 속성을 이긴다. `[hidden]{display:none !important}`를 함께 둔다.
- 질문을 다시 빌드하면 ID가 다시 매겨질 수 있다. 게시 후 추가분은 add 패치로 뒤 번호를 쓴다.
- 작성일·추가일을 코드에 고정하지 않는다(빌더 `b.ON`을 실제 날짜로).
- 회차 재작성으로 변경 이력이 '신규' 수백 건으로 덮이지 않게 일간 Diff 구조와 `--round`를 쓴다.
- 게시가 "읽지 않은 파일"이나 "더 새 버전" 때문에 거부되면, 최신본을 read로 읽고 그 위에 합쳐 다시 게시한다. 덮어쓰지 않는다.
- 정기 실행과 수동 작업이 같은 저장소를 고치므로 작업 전 항상 `git pull`.
- 경영진·외부 공유용 문장은 짧은 보고체, 줄표로 문장 잇지 않기, 비유·과장 없음, 약어는 처음에 풀어 쓰기.
